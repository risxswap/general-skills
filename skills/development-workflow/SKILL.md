# 开发流程

先读取目标项目的 AGENTS.md、README、已有词汇表、相关 Issue / Spec、ADR 与构建配置。保留已有修改，沿用已确认的项目决定。架构或技术栈未在适用的 `AGENTS.md` 中说明，或约定与代码冲突时，按 [项目约定](references/project-conventions.md) 处理：已有项目先分析实现，再与用户沟通确认；新项目引导选择，确认后按授权写入 `AGENTS.md`。

## 先确定任务模式

| 用户意图 | 本轮工作与完成条件 |
| --- | --- |
| 讨论、比较、设计方案 | 调查事实，说明方案、取舍和未决问题；完成方案讨论不等于获得业务实现授权 |
| 整理成规格、记录已讨论方案 | 按 [需求与缺陷](references/requirements-and-bugfixes.md) 的“整理需求规格”汇总已有结论，更新或创建 Spec；不自动实施或发布 Issue |
| 开发、修复、重构 | 在已授权范围实施并验证；保持重构的既有行为或落实明确的新行为 |
| 诊断、定位原因 | 按方法技能取得证据；仅定位时不修改业务代码，已授权修复时继续实施 |
| 审查、review | 固定代码范围并报告发现与缺口；已有修复授权才应用修改 |

从当前请求和已有授权判断模式，不要求用户每次选择。混合任务可分段执行，例如先审查再修复；“按照方案实施”可承接前文已确定的范围，不重新询问。讨论、仅整理规格和只审查模式跳过下面的实施步骤，完成相应产出后交付。

## 开发执行

1. 识别预期行为、受影响模块、现状和验收条件。缺陷先建立失败证据；需求中的未知行为不能用当前代码代替。
2. 业务术语、对象关系、状态或约束存在歧义或发生变化时，按需读取 [business-modeling](../business-modeling/SKILL.md)；规则明确的 CRUD 直接推进。按 [需求与缺陷](references/requirements-and-bugfixes.md) 处理会改变业务结果的未知项并决定记录粒度。继承已有决定和授权，不重复申请已获授权的开发步骤。
3. 涉及跨层字段或接口时读取 [契约协作](references/api-contract-collaboration.md)，确定成功、失败和兼容性，再修改两端。
4. 多步骤或跨层功能按 [行为切片](references/behavior-slices.md) 安排实施，每片先确定可观察结果和验证方法。局部修改直接作为一个切片，不额外生成计划文件。
5. Java 实现或审查读取 `java-backend`；前端实现或审查读取 `frontend-development`。混合任务分别读取必要分支，纯后端或纯前端任务不加载另一专项。
6. 每片按 [验证与交付](references/verification-and-delivery.md) 核对证据，再推进依赖它的步骤；最后检查相关跨片行为并报告结果和缺口。

专项已读取本流程时，沿用当前阶段，不循环路由。配套文件缺失时报告具体路径，继续不依赖它的事实调查，不自动安装依赖或复制另一套规范。

本流程按项目架构组织开发，不预设框架、分层或部署形态。安装目录和业务源码目录相互独立；操作命令在目标项目执行。

## 中文文档

生成或修改中文规格、计划、架构说明、README、技能文档或交付报告时，读取配套 [humanizer-zh](../humanizer-zh/SKILL.md)，先按事实起草，再校订本轮文字。润色不得改变规则等级、技术约束、代码、路径、授权、证据和完成状态。纯代码任务不额外启动文档润色。

## 方法技能

要求定位根因、复杂故障、偶发问题或性能回退时，读取 [diagnosing-bugs](../diagnosing-bugs/SKILL.md)；简单且原因明确的修复保留轻量路径。用户要求审查分支、PR、提交或当前修改时，读取 [code-review](../code-review/SKILL.md)，保持只审查范围，除非已有修复授权。方法技能与 Java 与前端规则配合使用，继承当前阶段，不循环启动流程；普通开发自检不强制完整审查会话。

Java 后端与前端专项随安装场景提供，属于可选路由。需要该专项时，先检查同一安装根下的 `<技能名>/SKILL.md` 是否存在；存在再读取，未安装时沿用项目规范并说明专项未加载，不把它当公共配套损坏，也不自动安装。
