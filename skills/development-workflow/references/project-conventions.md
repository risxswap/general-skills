# 技术设计与项目约定

产品场景、运行平台、架构与技术选型由目标项目的 `AGENTS.md` 说明。先读取适用于当前目录的项目约定，以及它指向的架构说明；已明确的决定直接沿用。技能提供工作方法和技术参考，安装场景只选择技能，不替项目决定技术栈。

## 缺少定义时

- **已有项目**：先检查构建配置、依赖与锁文件、目录结构、启动和部署配置，以及当前任务相关的调用链与测试。用具体文件说明实际框架、模块边界、分层职责和部署形态，区分可验证事实、推断与未知。向用户概括现状，提出延续或调整的建议，沟通确认哪些约定应记录；不能仅凭目录名认定架构，也不能把历史实现自动定为未来规范。
- **新项目**：按下文“新项目架构讨论”确认方案，不预设 MVC、Spring Boot、Vue 3 或 TypeScript。
- **定义与代码冲突**：指出具体差异及影响，确认是记录过时、实现偏离还是正在迁移；保留适用的原约定，不擅自改文档迁就代码或迁移技术栈。

向用户说明这些决定将作为 `AGENTS.md` 的项目约定。沿用会话中已明确的选择，不重复确认；尚未确认的选型只作为建议。等待必要选择期间继续独立调查和验证，依赖该选择的实现待确认后再推进。资料缺失不妨碍只读诊断和审查，也不能据此判定实现违反某种未约定架构。

## 新项目架构讨论

仅适用于从零开始的新项目，现有项目新增功能或较大业务模块沿用现有流程。即使已有部分技术选型，新项目仍需补齐尚未确认的架构与数据库设计；已有结论直接沿用。

先了解核心业务、使用人群、预计规模、部署环境和团队经验，再给出具体推荐及取舍理由，围绕关键分歧与用户讨论。讨论覆盖前后端技术选型、模块职责与依赖、主要业务流程，以及必要的接口交互、认证与权限、部署方案和首版实施范围。按项目规模控制深度，无前端或无后端时说明适用范围。

数据库设计在最初讨论中充分确认，不推迟到各模块开发时补齐。以当前约定的业务范围为边界，用 ER 图和表结构说明具体设计，并讨论：

- 数据库选型及理由。
- 核心实体、表结构、字段类型、必填项和默认值。
- 主外键、关联关系、唯一约束及业务约束。
- 主要查询方式与索引设计。
- 数据生命周期，包括状态变化、删除和归档。
- 事务边界，以及适用时的并发一致性、审计和数据隔离。

业务歧义先与用户厘清，不能用未经确认的表结构替代业务决定。非关系型存储采用对应的数据结构与约束说明；确实无需数据库时，与用户确认这一结论，不为满足清单引入存储。

完成条件：形成可供审阅的架构方案和数据库设计，用户已确认整体架构及数据库设计，影响搭建与编码的业务歧义已经解决。等待确认期间可继续需求调查和方案完善，项目初始化、业务编码和数据库迁移在确认后按已有实施授权推进；不把沉默或只确认技术栈视为全部确认。纯讨论任务仍止于方案交付。

按下文规则记录阶段性方案与已确认决定，详细设计保留在项目已有架构、数据库文档中。后续需求变化涉及设计调整时，说明影响，确认实质变更并同步更新设计，已确定内容不重复询问。

## 设计文档与项目约定

技术讨论收尾、用户表达阶段性认可或准备进入实施时，自动保存已有设计结论；未决项标明影响，未确认方案保存为草案。用户明确要求不写文件、仅回复草稿或只读时，在回复中交付。保存设计不代表确认或获得实施授权。

沿用目标项目已有文档位置；没有约定时，架构设计使用 `docs/01-项目总览/03-架构设计.md`，数据库设计使用 `docs/01-项目总览/04-数据库设计.md`。按实际内容记录技术选型、模块职责、依赖与部署，以及 ER 图、表结构、字段、约束、索引、生命周期与事务设计。无需数据库时记录已确认结论，不创建空设计。规模较大时再拆为 `docs/01-项目总览/04-数据库设计/`，内部按编号加中文模块名命名，并保留全局关系与导航。

长期设计保持稳定路径，正文记录最后更新日期，明确区分当前有效设计、拟议变化和实现现状。迁移脚本跟随代码，设计文档解释业务含义与选择理由并引用实现。新项目进入实施前按 [需求与缺陷](requirements-and-bugfixes.md) 完成需求落盘；实施后同步最终设计和真实验证状态。

已确认的项目执行约定同步到适用的 `AGENTS.md`；不存在时创建，保留原有内容及目录作用域，不同时创建大小写不同的重复文件。尚未确认的建议保留在设计草案中；明确要求不写文件或只读时，只在回复中提供建议段落。

按实际需要记录：架构与模块职责、技术栈与版本策略、数据库和持久层、前端产品场景、运行平台与组织方式、适用的编码规范，以及构建/测试配置和已有架构文档的位置。只写已确认内容，不生成空模板；能从配置读取的精确依赖版本引用配置位置，特殊版本限制与原因才写入约定。详细取舍沿用已有架构文档或 ADR，`AGENTS.md` 保留摘要与指针。

完成时说明已确认的约定、记录位置或待写入文本，以及仍影响当前任务的未决项。确认架构不等于授权重构整个项目。

## 重要技术决策

新项目方案确认、现有项目调整重要技术方案或用户要求记录决策时，保存影响长期实现且需要保留选择理由的决定，例如技术栈、数据库、架构边界、部署方式或一致性策略。普通命名和业务规则归入需求或领域文档，无需创建 ADR。

按设计讨论的记录边界，查找并沿用既有决策目录，没有约定时使用 `docs/04-技术决策/YYYY-MM-DD-中文主题.md`，日期取创建当天的用户当地日期。实际写入状态、背景、拟议或已选方案、理由、已讨论的备选方案和影响；未讨论的内容如实注明，不补造历史。跨天更新保持原文件名。同一决定复用已有记录，替代决定新建记录并相互链接，保留历史状态。

重要技术取舍已形成可归纳方案但尚未确认时，可保存草案 ADR；用户确认后更新状态。只审查或明确要求不写文件时在回复中交付。未确认选择不能标记为已采纳，调整既有决定时保留有效决定和历史记录。

交付前核对所需架构、数据库及 ADR 文件实际存在、内容覆盖本次决定、确认状态和实现状态分别记录、链接可解析。在已有导航或架构文档中链接实际记录；没有导航时可创建简短的 `docs/README.md`。报告实际路径与未决项，不以目录树替代文件。
