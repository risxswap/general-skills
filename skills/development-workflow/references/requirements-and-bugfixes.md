# 需求与缺陷

## 澄清边界

先查项目事实：已有权限模型、接口调用方、构建命令和同类实现由 Agent 调查。技术细节能在既有约束内合理决定时，直接选择并在有影响时说明理由。

未确定的业务规则、资源权限、不可兼容的接口或数据变更，以及会扩大范围的决定，若存在多种结果且会改变用户预期，应先澄清受影响部分。提问说明具体选择及影响；答案未到时继续不依赖它的工作，不把等待超时当成确认。

已有规格和本轮授权足以决定时直接推进。可逆、低影响的细节可以采用明确假设；不得靠假设决定资金计算、数据归属或破坏性迁移。纯讨论时保存方案及未决项即可，不因为方案已写完自动实现。

## 记录粒度

局部修改且行为明确：在当前任务说明范围、修改和验证即可。跨层功能、数据结构或架构变更：沿用项目文档目录，写简明规格与实施计划；项目没有约定时放入 docs 下的任务目录。文档数量按复杂度决定，不为填模板发明需求。

规格至少说明触发操作、用户可见结果、关键失败条件、权限、契约变化和不在本次范围的事项。计划按 [行为切片](behavior-slices.md) 列出依赖与必要验证；同一决定只维护一处。已有批准规格直接执行，发现实质冲突时报告影响并澄清冲突部分，继续独立工作。

## 整理需求规格

用户要求“整理成规格”或“记录刚才的方案”时，汇总已有讨论，不重新访谈。先定位相关 Spec，结合现有词汇表、ADR 和必要代码事实；更新已有文件，没有时按项目文档约定创建。用户只要求回复中的草稿时直接回复，不写文件。

按内容需要整理以下项目，篇幅与需求规模相称，不强制长用户故事列表或空章节：

- 问题与目标：用户遇到什么问题，希望获得什么结果。
- 预期行为：触发条件、成功结果及已明确的失败、权限和状态规则。
- 已定决定：已确认的接口、数据和实现选择，引用已有定义，不复制整份词汇表或 ADR。
- 验证方式：可观察的验收结果、已商定的测试范围及可复用的现有测试；计划执行与实际通过分开描述。
- 范围与未决项：明确不包含什么，以及尚未决定的内容及影响。

区分用户已确认决定、代码现状和未采纳建议；讨论过不等于批准。冲突或缺失先如实列出，允许交付含未决项的草稿，不为完成模板补造需求或将当前实现当成预期。已明确问题不重复提问；只有连整理对象都无法确定时才澄清该对象。

写完对照原讨论检查遗漏、扩大范围和确定程度，再按 humanizer-zh 校订中文。标明实际文件位置和剩余未决项。整理完成不表示规格已获批准，不自动拆实施计划、修改业务代码、创建或更新远程 Issue；用户明确要求的后续动作另按已有授权执行。

本分支借鉴 [上游 to-spec](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/engineering/to-spec/SKILL.md) 的已有讨论归纳方式，采用本地简明 Spec，保留 [MIT 许可证](LICENSE)。

## 缺陷

记录输入、实际结果、预期依据和可复现条件。优先构造最小复现；无法复现时明确证据缺口，不能把猜测当成根因。修复影响行为时补充能捕获原故障的回归检查，验证修复前失败、修复后成功；无语义修正不为覆盖率添加测试。

## 变更边界

局部修复保持已有框架、目录和公共接口。确需改变依赖、模型或接口时列出调用方影响。已确认的架构约定按 [项目约定](project-conventions.md) 记录，并区分目标与当前实现；描述实现现状的架构文档需有代码依据，拟议设计留在任务规格中。存量不符合本套默认规则不构成整仓迁移授权。
