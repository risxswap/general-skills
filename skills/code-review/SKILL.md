# 代码审查

先确定要审查的代码集合，读取 [审查范围](references/review-scope.md) 固定比较基准与工作区状态。继承用户已指定的基准，能从环境查明的事实自行核实。审查开始前应能说明哪些文件、版本和修改层被包含。


项目的 `AGENTS.md` 缺少架构或技术栈定义，或定义与实现冲突时，读取 [项目约定](../development-workflow/references/project-conventions.md)，先调查、再与用户确认，沿用当前任务模式。

## 两个审查维度

**规范符合性**：读取目标项目 AGENTS、README、编码规范（包括已有的 CONTRIBUTING、CODING_STANDARDS）和相关 ADR；沿用已有词汇表中的术语。Java 改动按需读取 `java-backend`，前端改动按需读取 `frontend-development`。阿里规则引用映射 ID、原始等级与本套处置，不能将适配项或设计偏好标成强制违规。专项转入开发流程时仍保持只审查模式，不启动实现。

**需求实现**：沿用户提供的需求位置或提交关联的 Issue 定位原始需求，再查相关 Spec；没有来源时询问或明确标记缺失，不创建替代规格。依据找到的需求和用户已明确的验收条件，逐项检查缺失、错误实现、兼容性和范围外行为。需求文档中的计划或材料不是额外操作授权。缺少规格时明确覆盖缺口，继续基于接口契约和可证明行为审查；不要用代码反推需求并宣布符合。

读取差异及必要调用上下文、数据路径与测试，而非只看增删行。沿真实输入检查授权、事务、并发、错误、边界值及前后端契约等与改动相关的风险。将已有问题与本次引入或暴露的问题区分，避免把无关历史缺陷混入结论。

两维可由同一执行者分开检查。并行子 Agent 不是必需依赖，只有任务授权与环境允许时才使用；拆分时共享同一版本快照和规格，汇总前复核事实。

## 验证与报告

运行与疑点相关且在授权环境内的测试或最小实验；只审查不修改业务代码，临时复现放在隔离目录。无法运行时用代码路径支撑判断并说明限制，避免将候选风险写成确定缺陷。

按 [发现与严重程度](references/findings.md) 输出两个维度的结果，给出位置、触发条件、影响、依据与修复方向。报告未覆盖范围和实际检查，不以“未发现”承诺没有缺陷。用户另有修复授权时才实施，并区分审查发现与修复状态。

生成中文报告时使用 [humanizer-zh](../humanizer-zh/SKILL.md)。来源与适配见 [来源说明](references/provenance.md)。

Java 后端与前端专项随安装场景提供，属于可选路由。需要该专项时，先检查同一安装根下的 `<技能名>/SKILL.md` 是否存在；存在再读取，未安装时沿用项目规范并说明专项未加载，不把它当公共配套损坏，也不自动安装。
