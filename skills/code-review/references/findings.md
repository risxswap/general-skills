# 发现与严重程度

每项可操作发现包含：简短标题、受影响文件及紧凑行范围、成立的输入或场景、用户或系统影响、代码/测试证据，以及最小修复方向。规范问题另给规则来源；需求问题给对应预期。尚不能确定的条件放入待核实问题，不以假设堆积缺陷。

| 等级 | 判据 |
| --- | --- |
| P0 | 无需特殊前提即可造成广泛严重破坏，需立即阻止交付；谨慎使用 |
| P1 | 常见或明确支持路径中的严重错误、越权、数据损坏等，应优先修复 |
| P2 | 有具体影响的普通缺陷或有依据的规范违反 |
| P3 | 影响较小的改进项；风格偏好单列建议，不伪装成缺陷 |

严重程度依据影响和触发概率，不直接将阿里“强制”映射为 P1。命名、抽象与重复代码等需要结合上下文，已有项目决定可以合理覆盖默认建议。工具已经可靠报告的格式问题简要引用结果，不用大量重复评论掩盖业务缺陷。

分别报告“规范符合性”和“需求实现”，各维按严重程度排序。同一问题影响两维时只维护一份详细发现，另一维引用编号，统计不重复。缺失规格写“需求维未完整评估”；未发现问题写明范围，不等价于所有测试通过。

报告最后列实际检查、未运行项和残余疑问。只审查时修复方向可以是文字建议，不自动应用补丁。行号以实际被审版本核对，未经验证不提供看似精确的位置。
