单体指后端作为一个应用交付；可以按业务模块组织代码，必要时使用多个构建模块。前端可以独立构建、部署，也可以由后端托管静态资源，按项目选择。单体不等于只能单实例运行，并发与数据库一致性仍需处理。

## 4. Java 单体技能

### 应用组织

新项目优先使用一个可运行 Spring Boot 应用，按业务包组织。包内按需要区分入口、业务服务、数据访问和契约对象。简单 CRUD 使用清晰的 Controller → Service → Repository/Mapper 调用关系；复杂业务仍以 Service 承载规则，按维护需要拆分方法或协作类；业务建模不要求 DDD 分层。

不强制每个 Service 配套 Interface/Impl，不强制多 Maven 模块，不因采用阿里规范就增加 DDD 全套目录。存量项目沿用已经成立的模块边界，局部任务不自动触发重构。

### 规则范围

| 参考主题 | 需要指导的实际决策 |
| --- | --- |
| Java 代码规约 | 命名、常量、空值、类型、equals/hashCode、集合、泛型、资源释放、金额与时间 |
| Spring Boot 单体 | 依赖注入、配置、Controller 边界、业务服务、异常映射、启动与关闭 |
| API 与安全 | 输入校验、错误语义、身份认证、对象级权限、敏感字段、上传、契约兼容 |
| 数据与事务 | 参数化查询、分页、索引、唯一约束、并发更新、事务边界、迁移与回滚 |
| 并发与任务 | 线程池容量、超时、中断、任务失败、重复执行和多实例竞争 |
| 测试与交付 | 业务单测、数据集成测试、事务与授权反例、构建和实际验证结果 |

Spring 事务代理、自调用、异常回滚、ORM 查询行为等细则，在实现参考文档时按选定框架版本核对官方文档。MyBatis、MyBatis-Plus、JPA 按项目实际依赖加载对应分支；MySQL 专属规则只对 MySQL 生效。

服务发现、服务网关、服务间 RPC 治理、分布式事务、服务网格、微服务拆分不属于本技能范围。Redis、消息队列、配置中心和分布式锁均不是基础依赖；真实业务需要时另行明确范围。对第三方 HTTP 调用仍需处理超时、失败及有副作用操作的重试语义。

### 阿里规范的来源与采纳

用户提供的[手册汇总仓库](https://github.com/edisonwd/alibaba-Java-development-document)包含多个版本及作者阅读笔记；笔记与原手册应区分。阿里巴巴官方 [P3C 仓库](https://github.com/alibaba/p3c)提供黄山版 PDF 和部分规则的检查实现。建议实现阶段以官方黄山版作为固定候选基线，同时保留用户给出的资料入口；首期已核对的规则及固定版本见技能内的来源映射。

实现时建立 `alibaba-rule-mapping.md`，每条被采用的规则记录：

| 字段 | 作用 |
| --- | --- |
| 规则标识 | 采用本套稳定编号，不冒充官方规则编号 |
| 来源定位 | 仓库、版本、文件、章节/条目，记录取得时的提交或文件摘要 |
| 原始等级 | 保留手册的强制、推荐、参考分类 |
| 本套处置 | 采纳、条件适用、适配或不适用，并说明理由 |
| 适用条件 | JDK、数据库、框架或业务条件 |
| 验证方式 | 静态检查、测试、人工审查或行为评测 |

不要把手册全文装入技能入口，也不要把本套建议标成“阿里强制”。原规则在本套中的调整必须可追溯；涉及版本或项目差异时说明影响，不能静默降低等级。

本套新增的 Spring Boot 实践单独标注来源。旧版手册里的 API 和工具建议需核对目标版本；格式化、命名规则复用现有工具，避免为了局部修复重排全仓。P3C 的检查只覆盖部分规范，扫描通过不能代表符合全部手册。

设计阶段只核对仓库说明；实施阶段已取得官方 PDF 并核对首期映射条目。未声明逐条覆盖全册，也未接入或测试 P3C 扫描器兼容性。

## 5. Vue 技能

新项目采用 Vue 3 / TypeScript；版本、构建工具、路由、状态库和 UI 库在具体项目中选定。存量项目以 package.json、锁文件和代码为事实来源，不因调用技能自动升级或迁移技术栈。

按任务覆盖：

- 组件职责与 props/emits 契约；可复用逻辑进入 composable，跨页面共享状态才考虑 store。
- API 客户端和类型边界；对齐可空字段、错误码、分页、日期时区、金额精度和大整数 ID。
- 加载、空数据、错误、成功、取消、重复提交，以及请求竞态和组件卸载。
- 表单校验、服务端错误反馈、路由返回/刷新、权限展示和键盘可操作性。
- 复用项目组件与样式约定，保持响应式和可访问性；不强制集团后台包。
- 类型检查、构建、受影响组件测试和真实浏览器验证；源码审查不等价于浏览器验收。

前端隐藏操作不替代服务端授权。认证、Cookie/Token 和跨域设置沿用真实接口契约，不预设 JWT 或 OAuth，也不根据单体架构推断认证方式。

## 6. 跨层开发流程

1. 建立事实：读取目标项目约束、构建配置、相关业务代码、数据库和已有测试。
2. 明确行为：写出用户操作、成功与失败条件；影响接口时确定字段、分页、错误、权限和兼容性。
3. 按规模组织：简单修复直接实施并验证；跨层功能或架构变更保存简明规格与实施计划，关键不确定性才需澄清。
4. 实施：后端维护接口实现与项目既有契约文档，前端按同一契约接入；接口改动同步检查两端。
5. 验证：按变更风险选择单测、集成测试、接口和浏览器检查，记录环境、命令、结果与未验证范围。
6. 交付：说明实现行为和限制；部署、生产迁移、外部系统写入按用户授权与环境规则执行。

接口文档沿用项目现有形式；有 OpenAPI 时同步更新，没有时提供最小可核对的契约，不强制引入代码生成工具。公共流程管理协作时机，Java/Vue 专项分别维护实现细则。

## 8. 验证与实施顺序

首期建议顺序：来源映射与 Java 入口 → Java 专项参考 → Vue 专项 → 公共流程与跨层场景 → 打包可用性检查。详细任务计划在技能实施时形成。

技能验收分为结构与行为两层：

- 结构：对每个技能运行 skill-creator 的 quick_validate；检查相对引用、配套文件和元数据。扫描工具接入前验证与项目 JDK/构建工具的兼容性。
- 行为：在隔离的最小项目中执行真实任务，观察修改范围、行为结果和验证证据。未实跑的场景标记为待验证，不以说明文字或关键词匹配替代。

| 场景 | 应观察到的结果 |
| --- | --- |
| 单体新增带分页的查询接口 | 沿用现有持久层，契约与查询一致，不引入微服务基础设施 |
| 多步写入中间失败 | 按业务边界回滚；验证失败后的数据库状态 |
| 并发更新同一记录 | 根据实际竞争条件保证业务约束，而非只添加进程内锁 |
| 用户访问他人业务数据 | 后端拒绝越权，前端能展示真实错误 |
| Vue 列表快速切换筛选 | 旧请求结果不覆盖当前筛选结果 |
| Java 长整型 ID、金额和日期传到前端 | 双端契约保留精度并明确时间语义 |
| 现有 Vue 2 项目的局部修复 | 沿用项目版本，不自动迁移 Vue 3 |
| 只修改 Java 方法或 Vue 组件 | 只读取必要专项规则，不启动无关全栈流程 |
| 缺少浏览器或数据库环境 | 明确未验证部分，不宣称集成或 UI 验收通过 |

后续独立 Agent 行为评测应另按当时的授权与工具条件执行，本轮不宣称已通过。

## 9. 实施前保留的决策

这些选择不阻塞技能结构设计，在创建新业务工程或启用专项工具时确定：

- JDK / Spring Boot 的具体版本及构建工具；存量项目沿用已有配置。
- 数据库、持久层、迁移工具及是否需要缓存。
- Vue 构建工具、UI 组件库、路由与状态库。
- 认证机制、前后端部署方式，以及是否存在多实例运行。
- 最终采用的手册版本，以及需要覆盖项目约定的规则清单。

优先交付可用于现有项目的技能，再根据真实新建项目需求添加模板和安装工具。
