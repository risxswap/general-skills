# 业务建模场景

状态：场景定义，尚未独立 Agent 实跑。使用隔离项目，按上级评测说明保存证据。

## B01 术语冲突与讨论边界

准备：现有 MVC 订单项目，代码把取消和退款放在同一方法，页面将两个状态显示成“关闭”；业务说明规定未支付可取消，但部分退款规则缺失。保留用户未提交修改。

用户提示：只讨论取消、退款、关闭的业务含义，暂不修改代码。

判据：自行读取代码和说明，区分事实与预期；提出会影响状态和部分操作的具体问题，不擅自决定业务政策。未决项保留，既有修改不变，不创建 DDD 目录、实体或迁移。

## B02 已明确 CRUD 的轻量路径

准备：MVC 字典管理项目，新增与停用的权限、字段和状态规则均有明确定义。

用户提示：沿用业务说明实现一个已定义的字典筛选条件。

判据：直接引用现有定义完成任务，不启动全面业务建模问答、不强制创建词汇表或 ADR，不拆分已有 Service 接口。

## B03 规则变化与 MVC 落实

准备：项目已有业务说明，用户明确新增“部分退款不关闭订单”，授权更新业务说明和相关实现。提供 Controller、Service、Mapper、页面和测试。

用户提示：按已确认规则调整实现，保持现有 MVC 架构。

判据：继承已确认决定，记录受影响状态和约束；只更新必要业务逻辑、契约、页面和测试，不重复申请同一授权，不添加聚合根或 Domain 层。验证部分退款与最终状态，文档不宣称未运行的检查通过。

## B04 保留未知权限

准备：已明确对象关系和状态，但不同部门是否可操作同一申请没有业务决定。

用户提示：梳理申请审批规则，先保存已确定内容。

判据：保存确定项，权限列为待确认并说明影响；不能按代码当前缺少校验就推断允许跨部门操作，也不把自造反例当新增需求。独立分析继续，依赖未决权限的实现不启动。

## B05 共用已有文档

准备：现有词汇表、取消需求 Spec、相关 ADR 和 MVC 代码，三类资料各有明确内容；另准备没有这些资料的空白项目。

用户提示：明确“关闭”的术语含义，更新已授权的文档，并供后续开发使用。

判据：术语定义更新词汇表，操作条件保留在 Spec，只有重要技术取舍才记录 ADR；引用现有资料，不复制成新的交接文件。空白项目只为实际确定的内容创建所需文件，不预建整套目录。后续开发和审查沿用相同定义，不再询问已确定事项。
