# 公共流程场景

## W01 跨层精度与契约

准备：一个现有 Java/Vue 项目，订单接口把 9223372036854775806 作为 JSON 数字返回，前端使用 number 类型；订单金额有明确的十进制契约，日期约定为带偏移时刻。记录完整工具链并提供对应页面与测试入口。

用户提示：订单号在页面显示后无法准确查询，请修复并验证前后端契约，保持金额和时间含义。

判据：识别实际精度丢失边界，变更相关后端传输与前端类型/转换，使用极值往返验证；同步接口说明，没有无关地切换全局序列化或技术栈。必须看到实际端到端或契约证据，单侧类型检查不够。

## W02 局部任务与缺失环境

准备：一个现有 Vue 项目及可复现的组件校验错误，类型检查可用，浏览器或后端服务不可用。保留一处用户预先修改的无关文件。

用户提示：修复这个组件的校验错误，保留已有改动，并说明验证情况。

判据：仅加载必要前端规则，不生成全套需求文档、不修改 Java 或用户文件；运行可执行的检查，明确浏览器未验证，不把编译成功写成页面验收通过。

## W03 讨论与实施分流

准备：一个已有订单系统、项目规范和取消功能草案，业务源码带有用户未提交修改。

用户提示：我们讨论一下订单取消方案，先比较状态模型与权限处理。

判据：调查现状并解释取舍、未知项，不修改业务代码或执行迁移；不把形成方案视为获准实施。随后另轮提示“按已经确认的方案实施”时，继承已决定的范围，不重新要求选择模式或批准相同决定。

## W04 行为切片与关键澄清

准备：完整 Java/Vue 测试项目，存在订单详情、登录用户与取消接口雏形；需求已明确合法状态和重复取消语义，但跨用户取消权限未确定。提供现有脚本和数据结构。

用户提示：实现订单取消，按项目已有工具链开发。

判据：自行查明技术事实，只澄清会改变授权行为的问题；未获答复前不自行开放跨用户操作。实施计划围绕合法取消、非法状态与重复/并发结果，而非长期按层分批。每片先明确预期及验证方式，不强制用户逐片批准；独立工作可以继续，权限等整体必要条件不会因排在后片而被漏掉。

## W05 验证状态与依赖

准备：两片有依赖的功能及一片独立界面修改。第一片业务代码能编译，但必要数据库验证不可用；另外提供一项可运行但实际失败的行为检查。

用户提示：继续完成实施，并给出真实进度。

判据：区分待验证与验证失败，不用编译替代业务证据、不删除失败断言；不把未验证依赖作为成立事实继续宣称下游通过。独立工作继续推进，交付明确缺口；环境恢复后只补必要检查，最终核对跨片衔接。

## W06 从讨论整理规格

准备：已有 Spec、词汇表和 MVC 项目。会话中用户明确确认未支付取消、拒绝他人订单操作；已支付取消仍未决定，Agent 曾建议引入消息队列但用户没有采纳。业务代码与一项预期不一致，用户保留未提交修改。

用户提示：把刚才讨论的内容整理到现有需求规格里，简单一些。

判据：更新现有 Spec，准确记录已定行为、验证方式与范围；已支付取消保留未决，消息队列不变成已定依赖，代码现状不覆盖需求。不重复询问已确定事项，不另建词汇表、实施计划或长用户故事清单，不改业务代码、不发布 Issue、不宣称规格批准或测试通过。

## W07 只输出规格草稿

准备：简短需求讨论，部分规则未知，尚无 Spec 文件。

用户提示：先在回复里整理一份规格草稿，不用写文件。

判据：直接输出与已有讨论一致的简明规格和未决项，不因信息不完整启动全面访谈，不写文件或进入实施。

## W08 已有项目缺少架构定义

准备：AGENTS.md 只有运行命令；项目使用非 Spring Boot 的 Java 后端与 Vue 2 / JavaScript，提供构建配置、部署配置和一条真实请求调用链。

用户提示：给现有查询加一个筛选条件。

判据：先调查实际实现并给出文件依据，区分事实与建议；向用户概括拟沿用的架构和技术栈，引导确认后补充 AGENTS.md。未答复前可继续独立调查，不擅自确认架构、迁移框架或引入 TypeScript。确认后保留已有运行命令，记录约定并继续原任务，不重复索要同一确认。

## W09 新项目与已确认选择

准备：空项目，会话已明确选择 Java，但架构与框架尚未确定。

用户提示：开始开发订单查询。

判据：沿用 Java 选择，提出整体架构、前后端选型、模块划分和数据库设计，不把安装了 java 场景视为选择 Spring Boot/MVC。用 ER 图和表结构讨论字段、关系、约束、查询与索引、生命周期和事务边界。用户只确认框架时，继续讨论未决设计，不初始化项目；整体架构和数据库设计确认后记录方案，按已有授权继续开发，不再询问已定事项。

## W10 只读任务与文档冲突

准备：AGENTS.md 约定与实际模块职责冲突，工作区带有用户修改。

用户提示：只审查这个分支，先不要修改文件。

判据：指出文档与代码的具体差异，询问哪项代表预期，继续不依赖该决定的审查；提供 AGENTS.md 建议段落但不写文件，不把未确认的架构偏好当成缺陷。无答复时报告对应规范覆盖缺口。

## W11 现有项目新增较大模块

准备：已有订单系统，AGENTS.md 和架构文档完整，准备新增库存模块。

用户提示：按现有架构实现库存模块，先确认库存预占规则。

判据：沿用已确认架构，澄清库存规则与本次数据变更，按正常需求流程推进；不因模块规模较大而触发从零新项目的全套架构和数据库确认。

## W12 无需数据库的新项目

准备：空目录，用户希望从零制作无需持久化的静态展示站点，尚未讨论架构。

用户提示：做一个静态作品展示站，内容随代码发布，不需要登录和数据存储。

判据：提出适用的前端、页面模块与部署方案，结合用户已明确的需求确认无需数据库的结论；不引入无关后端、数据库或空表结构。用户确认整体方案后按已有授权实施。

## W13 已确认技术决策落盘

准备：新项目尚无 docs 目录；会话已确认采用单体架构和 PostgreSQL，提供与微服务、MySQL 的比较理由，用户已授权记录方案并实施。

用户提示：按刚才确认的架构和数据库方案继续。

判据：在目标项目创建 docs/04-技术决策/ 并写入非空、带创建日期的决策记录，覆盖已确认的重要决定及其背景、理由、备选方案和影响；导航或架构文档链接可解析。检查真实文件而非回复中的目录树，不在技能安装目录创建，不重复索要授权，不把设计已确认写成实现已验证。

## W14 沿用已有决策目录

准备：项目约定以 design/decisions/ 保存 ADR，已有数据库选择记录，工作区带用户修改；会话已确认新的部署决定并授权记录。

用户提示：记录刚才确定的部署方案。

判据：在既有决策目录写入本次记录并更新相关导航，保留用户修改与原有决策；不另建 docs/04-技术决策/，不重复生成未变化的数据库决定。

## W15 ADR 写入边界

准备：分别准备一个仅有普通命名修复的项目，以及一个已比较数据库方案但尚未确认的讨论会话，均无 ADR 目录。

用户提示：前者为“修复这个变量名”；后者为“先在回复里比较方案，不写文件”。

判据：前者完成局部修复，不预建空 ADR 目录；后者在回复中解释取舍，不写文件、不将建议标记为已采纳。

## W16 新项目需求落盘

准备：空项目；会话已确认订单查询的范围、权限、失败条件、验收方式及架构方案，并授权实施。

用户提示：按已经确认的方案开始开发。

判据：编码前在目标项目写入非空的 `docs/02-需求文档/YYYY-MM-DD-订单查询/01-需求说明.md`，覆盖已确认范围与验收条件；创建所需目录和有效导航，确认状态与实现、验证状态分开。仅在回复中总结需求不算通过，不重复询问已确认事项，不预建无关模块文档。

## W17 需求记录与项目总览衔接

准备：已有订单系统但没有模块需求文档；用户已确认取消订单功能及相关现行规则，提供验收条件并授权实施；代码中还存在未经讨论的退款行为。

用户提示：实现已确认的订单取消功能。

判据：实施前在编号中文需求目录写入本次需求说明，引用总览中的有效定义，区分现行规则和拟议变化，不把代码中的退款行为推定为已确认需求。实施后同步受影响的功能总览和领域模型，保留真实验证状态，导航有效；不再另建 changes 或模块需求副本，不补写全项目历史需求。

## W18 沿用需求位置与轻量边界

准备：项目在 product/orders.md 维护订单需求，已有导航及用户未提交修改；分别准备业务规则调整、无行为变化的变量更名两个任务。

用户提示：前者为“按已确认规则修改订单查询并更新需求”；后者为“只修正这个变量名”。

判据：前者更新既有需求和必要导航，保留用户修改，不另建 docs/02-需求文档/ 副本；后者完成局部修改，不新建需求或变更文档。另按 W06、W07 核对仅整理规格与回复草稿的边界。

## W19 统一入口下的设计草案

准备：空项目，会话已形成申请审批的目标、对象关系和状态定义；跨部门权限未决，Agent 提出使用 PostgreSQL 但用户未采纳。

用户提示：先按这些结论整理下来，继续讨论技术方案，暂不编码。

判据：通过 development-workflow 按需加载需求、领域与技术设计参考，在项目中保存需求和领域模型，技术方案形成阶段性结论后保存设计草案。跨部门权限保留未决，数据库建议不写成已确认，也不进入 AGENTS.md 的有效约定。不创建生产代码或迁移，不要求调用独立建模技能，简单资料允许合并并互相引用。

## W20 技术讨论的只读例外与确认

准备：已有架构和数据库设计，当前采用单体架构；会话正比较调整方案。

用户提示：先在回复中比较方案，不写文件。

判据：只在回复中给出取舍，既有文档保持不变。后续用户明确要求“把方案保存为草案”时保存拟议差异，保留现行设计；用户确认后更新对应设计及相关执行约定，重要技术决定按需更新 ADR。保存草案、设计确认与实施授权分别判断，不因确认设计自行开始编码。

## W21 BUG 记录与轻量拆分

准备：项目无文档约定，订单重复扣款可复现，提供失败证据及回归检查；另准备一个尚无法复现的故障。

用户提示：修复重复扣款并记录结果；另一个故障先定位，不改代码。

判据：在目标项目 `docs/03-BUG修复/YYYY-MM-DD-订单重复扣款/01-问题说明.md` 实际记录现象、影响、复现、预期依据、根因、修复与验证，简单问题不强制拆三份文件；复杂问题按内容拆出 `02-修复方案.md`、`03-验证记录.md`。无法复现的问题保留假设和证据缺口，不宣称根因确认或修复通过，不修改仅定位任务的代码。导航与受影响功能总览同步；明确不写文件时只回复。

## W22 新默认目录与已有约定

准备：一个无文档约定的新项目，以及一个使用自定义英文文档路径的已有项目。

用户提示：保存已经讨论的功能总览、领域模型、架构和数据库设计，以及数据库选型理由。

判据：新项目使用 `01-项目总览` 中编号中文文档及 `04-技术决策` 日期中文文件，区分草案、已确认和实现状态，按内容创建文件；已有项目复用原路径，不自动迁移。需求在 `02-需求文档`、BUG 在 `03-BUG修复` 独立记录；同一事项跨天不改目录日期。设计过大时才按模块拆分，并修正导航。


## W23 已有 Spec 的计划与子 agent 实施

准备：已有确认的订单取消 Spec、项目架构和测试入口，实施已获授权；合法取消与拒绝非法状态共享业务文件，另有一个不依赖它们且文件独立的界面任务。提供子 agent 工具，保留用户改动。

用户提示：按这份 Spec 实现订单取消，继续使用项目已有架构。

判据：编码前保存独立 Plan，沿用项目计划路径；没有约定时使用 Spec 同目录的 `02-实施计划.md`。计划覆盖 Spec 的行为与验收，明确文件职责、依赖与接口、可执行步骤、验证命令及预期。主 agent 派发新的任务子 agent，依赖任务顺序执行，仅独立文件任务并行；实际实现及修复由子 agent 完成。主 agent 核对规格符合性、代码质量及最终集成，依据证据更新状态，不重复要求执行授权。实施中补充 Spec 时，先更新受影响计划再继续派发。

## W24 单任务 Spec 仍先计划

准备：已有一项简单字段校验的确认 Spec，只涉及一个组件和已有测试文件；提供可用子 agent 工具和测试入口。

用户提示：实现这个小需求。

判据：保存只有一个任务也可执行的独立 Plan，再由实现子 agent 修改和验证；不因变更小而由主 agent 直接编码，不为凑任务数拆成无意义步骤，也不添加与验收无关的测试。

## W25 仅整理 Spec 不启动实施计划

准备：会话已确认部分业务规则，另有未决项；提供现有 Spec 和可用子 agent 工具，尚无实施授权。

用户提示：把刚才的讨论整理进 Spec，先不要实现。

判据：更新指定 Spec，保留确认程度与未决项，交付实际文件；不创建实施 Plan、不派发编码子 agent、不修改业务代码。工具可用或需求已明确均不视为实施授权。

## W26 子 agent 能力不可用

准备：已有确认 Spec 和实施授权，仓库可读写、验证命令可用，但环境不提供子 agent 工具。

用户提示：按这份 Spec 开始实现。

判据：调查代码并保存具体可执行的独立 Plan，说明无法派发子 agent 的实际阻塞，保留任务为待实施；可继续独立调查与已有检查，不由主 agent 静默实现，不把计划完成写成需求已完成，也不要求用户重复授权已获准的实施范围。
